# 通信与资源规范

## 1. 所有权

| 范围 | 所有者 |
|---|---|
| `docs/基础设施/v5/V4Pf/` | V4Pf agent |
| `docs/基础设施/v5/V4vf/` | V4vf agent |
| `docs/基础设施/v5/协作/V4Pf状态.md` | V4Pf agent |
| `docs/基础设施/v5/协作/V4vf状态.md` | V4vf agent |

任何 agent 不得编辑对方独占文件，包括替对方勾选 ACK。回复必须写入自己的状态文件。

以下属于公共资源：

- `docs/基础设施/v5/main_v5.md`；
- 现有公共训练脚本和 `src/YingMusicSinger/` 下的既有模块；
- 已有 checkpoint、token、缓存和评测产物；
- 服务器 GPU、tmux session` 或 `midi_p` 标识；V4vf 新文件统一使用 `v4vf` 或 `random_init` 标识。

## 2. 消息协议

消息 ID：

- V4Pf 发出：`PF-001`、`PF-002`……
- V4vf 发出：`VF-001`、`VF-002`……

消息写入发送方自己的状态文件，字段至少包含：

```text
ID | 时间 | 类型 | 内容 | 需要对方 ACK | 状态
```

类型使用：

- `INFO`：通知，不阻塞；
- `REQUEST`：请求公共修改或资源，收到 ACK 前不得执行；
- `ACK`：确认对方某条消息；
- `BLOCK`：发现冲突或阻塞；
- `RELEASE`：释放文件或服务器资源；
- `RESULT`：共享可复用结论、接口或产物。

ACK 示例：V4vf agent 在 `V4vf状态.md` 写入 `ACK PF-003`，不得编辑 `V4Pf状态.md`。

## 3. 文件修改规则

### 3.1 独占路径

所有者可直接编辑。涉及对方需要复用的接口时，发送 `INFO` 或 `RESULT`。

### 3.2 新增代码文件

使用分支专属名称即可直接创建，但创建前仍需搜索同名文件。不得复用对方的输出目录或脚本名。

### 3.3 公共既有文件

执行顺序：

1. 在自己的状态文件发送 `REQUEST`，列出绝对路径、拟改符号和原因；
2. 对方在自己的状态文件 ACK，或提出冲突；
3. 修改者重新读取文件最新内容；
4. 只做声明范围内的最小修改；
5. 完成后发送 `RELEASE`，附修改摘要和验证结果。

未收到 ACK 不修改公共既有文件。紧急修复由用户明确指定所有者后例外。

`main_v5.md` 的纯索引追加可不等待 ACK，但必须先读最新文件、只追加自己的行，并在完成后发送 `INFO`。

## 4. 服务器资源规则

启动任何 GPU 任务前，发送 `REQUEST` 并登记：

```text
服务器 | GPU 编号 | tmux session 日志路径 | 预计开始 | 预计时长
```

必须同时满足以下条件才可启动：

1. 对方已 ACK GPU 分配不冲突；
2. tmux session 已检查服务器当前 GPU 进程和 tmux session `RELEASE`。资源不会因预计时长到期自动释放；只有明确 `RELEASE` 或用户裁决才算释放。

长任务必须使用 tmux session

## 5. 共享产物

- 共享 checkpoint 和数据只读复用，不移动、不重命名、不覆盖。
- 新产物写入分支专属目录。
- 需要清理大文件时先发 `REQUEST`，列出绝对路径、大小和可恢复来源。
- 不在协作文档记录密码、token、私钥或临时凭据。

## 6. 冲突处理

发生以下任一情况立即停止相关操作并发送 `BLOCK`：

- 双方声明同一 GPU、tmux session 发现来源不明的代码或文档变化影响当前任务；
- 需要改变双方共同依赖的 MIDI_P 定义、训练配方或评测协议。

双方无法通过状态文件达成一致时，由用户裁决。等待裁决期间可以继续不涉及冲突资源的工作。

## 7. 检查频率

至少在以下节点读取双方状态文件：

- 开始一轮工作时；
- 修改公共文件前；
- 启动、恢复或停止服务器任务前；
- 生成共享 checkpoint 或评测包前；
- 向用户报告最终结果前。

状态文件不是高频聊天工具。只记录会影响接口、资源、结论或执行顺序的信息。
